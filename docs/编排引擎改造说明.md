## 1. 改造前后对照

| 维度 | 改造前 | 改造后 |
|---|---|---|
| 流程定义位置 | `core/engine.py` 里的 `if node_id == "router" / elif "coder" / elif "fixer"` | `workflows/*.yaml`（引擎零业务分支） |
| 新增一个节点 | 改 Python：加 `elif` + 加 `create_task` 调用 | 改 YAML：加一个 `nodes:` 条目 + 指向它的边 |
| 条件分支 | 代码里 `if "[CODE]" in intent` | YAML `routes: {"[CODE]": coder}` |
| 循环 / 异常回退 | 代码里 `if retry >= 2` | YAML `on_failure` 回边 + `max_retries` 预算 + `on_exhausted` 兜底 |
| Agent 定义 | `engine.py` 顶部的两个 Python 字符串常量 | `agents/*.yaml`（角色/模型/工具集/记忆策略/版本） |
| 拓扑图 | `app.py` 里手写死的一串 Mermaid 字符串 | `workflow.to_mermaid(spec)` 由 YAML 生成 |
| 人工恢复目标 | `app.py` 里写死 `create_task(trace_id, "fixer", ...)` | `human` 节点的 `on_resume` 字段 |
| 并发分支 | 不支持 | `parallel: [a, b]` 扇出 + `type: join` 汇合 |
| 子流程嵌套 | 不支持 | 字段与校验已就位，**执行展开暂未实现**（见 §7） |

一句话：**编排从「代码」变成了「数据」**。`core/engine.py` 里已经搜不到任何业务节点名。

## 3. 节点字段全表

```yaml
nodes:
  - id: verify                # 必填，节点唯一标识
    type: tool                # llm | tool | join | human（默认 llm）
    label: 物理验收锚点        # 图上显示名

    # —— 类型专属 ——
    agent: coder              # type=llm：引用 agents/*.yaml 的 name
    tool: execute_spec        # type=tool：引用 core/tools.py 的 TOOL_REGISTRY
    join: [branch_a, branch_b]# type=join：等这些节点都 done 才放行
    wait_timeout: 120         # join 最长等待秒数

    # —— 上下文 ——
    context: "{spec}"         # 模板占位符：{prompt} {spec} {last_error} {files} {advice} {retry}
    publish: spec             # 成功后把输出写入 trace 工作记忆的哪个变量

    # —— 控制结构 ——
    routes:                   # 条件分支：输出里出现该标签就去对应节点
      "[CODE]": coder
    next: chat_reply          # 默认后继（同时是 routes 的兜底）
    on_success: done          # 成功目标（优先于 next）
    on_failure: fixer         # 失败目标（指回上游即构成循环）
    max_retries: 2            # 失败重试预算
    on_exhausted: human       # 预算耗尽的兜底目标
    parallel: [a, b]          # 成功后并发扇出
    on_resume: fixer          # type=human：人工介入后回到哪
    sub_workflow: other       # 子流程（预留，见 §7）
```

保留字：`done` / `failed` 是**终态标记**，不是节点。写 `on_success: done` 表示工作流在此成功结束。

## 4. 控制结构 ↔ 赛题要求

| 赛题要求 | 实现 | 位置 |
|---|---|---|
| 顺序执行 | `next` / `on_success` | `plan_transitions()` |
| 条件判断 | `routes` 标签匹配 + `next` 兜底 | `match_route()` |
| 循环迭代 | `on_failure` 回边 + `max_retries` 预算 | `plan_transitions()` |
| 并行分支 | `parallel` 扇出 | `_advance()` |
| 分支汇合 | `type: join` + 延迟轮询（`ready_at`） | `_join_state()` / `db.claim_task()` |
| 子工作流嵌套 | 字段与校验就位，执行展开未实现 | — |
| 人工介入节点 | `type: human` → `waiting_human` → `on_resume` | `_advance()` / `resume_with_advice()` |
| 超时 / 异常回退 | 节点异常按 `on_failure` 走；僵尸任务自动续跑 | `_step()` / `recover_stale_tasks()` |

### 循环计数器为什么「成功也带下去」

`code_gen` 里把重试预算挂在 `verify` 节点上（`max_retries: 2`），而不是 `fixer` 上。
因为 `fixer` 的 LLM 调用本身总是成功（它只是生成文本），真正的失败由下一跳的 `verify` 判定。
如果成功时把计数清零，`fixer → verify` 这一对就会永远打转。所以：

- **失败**：`retry + 1`，超过 `max_retries` 就跳 `on_exhausted`
- **成功**：计数原样带到下游

这样 `verify` 第 3 次失败时才会熔断，恰好对应旧版「coder 失败 1 次 + fixer 跑 2 次后转人工」的行为。

## 5. 怎么加东西（三个最小例子）

### 5.1 加一个 Agent
```yaml
# agents/reviewer.yaml
name: reviewer
label: 评审 Agent
version: 1
tools: []
memory: trace
role_prompt: |
  你是代码评审专家。请指出下面代码的缺陷，按严重程度排序，不要重写代码。
model: deepseek-chat
temperature: 0.1
```

### 5.2 加一个节点（接在验收通过之后）
```yaml
  - id: review
    type: llm
    label: 评审 Agent
    agent: reviewer
    context: "{files}"
    next: done
```
然后把 `verify` 的 `on_success: done` 改成 `on_success: review`。**全程不碰 Python。**

### 5.3 加一条新工作流
复制 `workflows/code_gen.yaml` 改名，改 `name` / `entry` / `nodes` 即可。
前端侧边栏会自动出现这个工作流（`list_workflows()` 扫描目录），管理员也可直接
调用 `engine.start_workflow("新名字", prompt)`。

| 渲染 | Mermaid 由 YAML 生成、状态上色、每节点都在图里 |

### 6.2 与旧引擎的行为等价性（打桩对比）

同一组打桩（LLM 固定返回、工具按脚本返回成功/失败）下跑四个场景，对比旧引擎（git HEAD）
与新引擎：

| 场景 | 旧 LLM 序列 | 新 LLM 序列 | 真实执行次数 旧/新 | 终态 |
|---|---|---|---|---|
| 一次通过 | router,coder | router,coder | 1/1 | done |
| 失败一次后修复 | router,coder,fixer | router,coder,fixer | 2/2 | done |
| 失败两次后修复 | router,coder,fixer,fixer | router,coder,fixer,fixer | 3/3 | done |
| 始终失败→熔断 | router,coder,fixer,fixer | router,coder,fixer,fixer | 3/3 | waiting_human |

**结论：调用序列、真实执行次数、终态完全一致。** 唯一差异是收尾任务行由 `coder/fixer`
变成了显式的 `verify` 节点——这正是「生成」与「验收」在编排层被拆开的收益。

### 6.3 老数据库兼容
对现网 `aegis_platform.db` 的副本执行 `init_db()`：

- 21 条历史任务、65 条历史日志完整保留；
- 自动补齐 `workflow / priority / ready_at` 三列，历史任务 `workflow` 为 NULL 时回退到 `DEFAULT_WORKFLOW`；
- 在迁移后的库上直接跑通一条新的 `code_gen` 流程（router → coder → verify 全 done）。

## 7. 已知边界（写进方案书时不要夸大）

| 项 | 状态 |
|---|---|
| `sub_workflow` 子流程嵌套 | 字段解析与「文件存在」校验已实现，**引擎暂不展开执行** |
| MCP / Function Calling | Agent 的 `tools` 目前是能力画像（注册与展示），**尚未作为 Function Calling 调用面** |
| 记忆管理 | 仅 trace 级工作记忆（`trace_vars`），无跨任务长期记忆 / 向量库 |
| 并发 | Worker 数 `WORKER_COUNT=1`（认领已原子化，调大即可并发）；`join` 去重标记依赖单 Worker，多 Worker 下存在极小重复放行窗口 |
| 沙箱 | 生成代码仍是**进程级**执行（资源与密钥隔离未做），不是容器级沙箱 |
| 工作流版本 | YAML 有 `version` 字段但未做「同版本并行/灰度」 |
